# Temi 테스트 화면 프레임 지연 개선 기록

## 문제와 측정 방법

낙상 테스트에서 스켈레톤이 느리게 움직이고 빠른 움직임을 놓치는 현상이 있었다. 앱의 최소 전송 간격은 200ms이지만 이전 요청이 끝나기 전에는 다음 프레임을 보내지 않으므로 실제 간격을 측정했다. Temi와 노트북은 같은 2.4GHz 핫스팟을 사용했고, 테스트 서버의 낙상 진단은 `FALL_DEBUG=csv`로 기록했다. 앱의 `PoseTiming` 로그와 서버 `frames.csv`를 세션별로 집계했다.

## 원인과 변경

기존 YUV 변환은 640×480 프레임의 각 픽셀을 `ByteBuffer.get()`으로 개별 접근했다. 버퍼의 행 간격과 픽셀 간격은 유지하면서 행 단위로 복사하고 필요한 색상 값을 NV21로 재배치했다. 영상 회전, JPEG 품질, 해상도 및 최대 전송 빈도는 바꾸지 않았다. 패딩, 픽셀 간격, 버퍼 시작 위치와 NV21 색상 순서는 단위 테스트로 확인했다.

## 측정 결과

| 항목 | 변경 전 중앙값 | 변경 후 중앙값 | 변화 |
| --- | ---: | ---: | ---: |
| 낙상 테스트 JPEG 변환 | 337ms | 82ms | 약 76% 감소 |
| 낙상 테스트 요청 간격 | 480ms | 228ms | 약 53% 감소 |
| 리듬게임 테스트 JPEG 변환 | 329ms | 84ms | 약 74% 감소 |
| 리듬게임 테스트 요청 간격 | 476ms | 234ms | 약 51% 감소 |
| 낙상 서버 MediaPipe 추론 | 49ms | 49ms | 변화 없음 |

요청 간격 중앙값을 단순 환산하면 낙상 테스트는 약 2.1회/초에서 약 4.4회/초로 증가했다. Temi 앱 로그 표본은 변경 전 낙상 32개·리듬 109개, 변경 후 낙상 54개·리듬 122개다. 일부 로그는 Logcat 버퍼에서 사라졌으며 전후 측정 시간과 동작이 완전히 같지는 않다. 서버 추론값은 별도 낙상 서버 로그 기준이다. 이 수치는 처리 속도이며 낙상 감지 정확도 개선을 뜻하지 않는다.

## 남은 지연과 제한

약 5초마다 응답이 늦어지는 현상은 남아 있다. 개선 후 102개 요청을 추가로 측정했을 때 응답 헤더 대기 중앙값은 93ms였고 일부는 681~903ms였다. 최초 요청은 2,041ms였다. 같은 시각 서버에서는 프레임 도착 간격이 길어졌지만 도착 후 처리 시간은 대체로 100ms 미만이었다. 별도의 Temi 핑에도 주기적 지연이 관찰됐다. 요청 전송 완료 이벤트는 OS에 데이터를 전달한 시각이므로, 이 결과만으로 핫스팟·Temi·노트북 중 원인을 확정할 수 없다.

서버의 낙상 FSM은 관측 간격이 750ms를 넘으면 관찰을 초기화할 수 있다. 재측정한 한 낙상 세션에서는 이런 초기화가 두 번 발생했다. 더 빠른 낙상 인식률, 다른 기기·네트워크에서의 재현성, 보라색 화면의 원인은 확인하지 않았다. 로그 수집 자체의 부하도 측정에 포함된다.
